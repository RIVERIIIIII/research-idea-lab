## 通信与光资源（静态代码事实）

- `paper_evaluator.py:1586–1623`：在配置故障后骨干子图中，为每个无序DC对求最短路径，即全对逻辑通信；不是显式执行ring reduce-scatter/all-gather阶段。
- `common_utils.py:729–770`：每对通信时间用模型参数×精度的数据量、DC数量、带宽及传播时延计算。`paper_evaluator.py:1769`直接调用。不能把此标量解释为已经实现集合通信完整轮次/依赖；`alpha_mode`配置的存在也不证明该路径实际使用了相应步数因子。
- `paper_evaluator.py:1690–1789`：路径分配记录波长ID、公共可用波长和链路冲突；逐对分配时将链路波长放入占用集合。`1854–1895`支持指定通信对增量加波长。此处是一次评估内的静态分配，没有按计算/通信阶段给出占用日历。
- `data/training_topologies.yaml`显式指定failed_link_id和replacement_link_ids；评估故障前后配置，不是模拟故障恰好发生在某个梯度传输中途的恢复过程。
- `data/paper_experiment.yaml`含模型、站点资源比例、波长可用profile和ssp_bound=0；硬件与故障配置可作模型输入，不是实际训练测量轨迹。

## 与论文模型需核对的两处对应

### 指标表达

论文§2.1：每DC base为local执行时间加其最大通信时间，T_iter为max(base)，最大同步等待为max(base)−min(base)。

当前评估器第1199–1206行先构造相同形式的base_step_time_by_dc，但将`_simulate_ssp`返回的平均迭代时间丢弃，最终使用 `t_local_max + t_inter + t_stall`。其中stall来自若任一DC停等便累计的系统停等区间，除以步数。它与论文max(base)的定义不是直接同一表达。

这需要核对定稿代码/结果口径；本轮未运行，不能据此直接判定所有图或论文结果错误，也不把它自动修正为其他公式。

### 计算补偿与选择目标

顶层`evaluate_state:313–397`的pure_compute/joint调用TP扫描（2209起），以t_iter为先的候选选择（1344起）。相对地，`result/paper/figure/analyze_topo2_dp_group_compensation.py`使用extra_dp_capacity_per_dc与optimal_t_iter放置；联合分析脚本含逐DP组/波长动作及恢复后stall排序（candidate_key）。后者更贴近论文摘要动作。

因此需识别最终使用的分析脚本、配置和结果文件，不能把旧入口中的TP调整反向改写为第一点已确认的贡献边界。源码文件名或函数名均不能替代调用链核对。

## X03能得到什么、仍缺什么

可以获得每DC局部耗时估计、每对通信时长/路径/波长、资源上限和整步进度模型。现有已读路径未提供：

1. 真实或显式依赖驱动的梯度就绪、bucket/集合通信分段及其开始/结束。
2. 计算通信重叠、可推迟通信的截止和不会延长迭代的余量。
3. 光资源随阶段变化的占用/释放日历、备份调用与切换事件。
4. 故障发生时刻与正在执行的通信块、下一轮同步和恢复路径之间的联动。

所以不能把模型中的DC等待时间直接作为可用于TSBPP共享的通信空闲时间。代码可作为后续模型基础；能否形成第二点仍取决于真实任务控制如何改变光保护决策及已有机制差异。
