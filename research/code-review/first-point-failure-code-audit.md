## 调用链与实际粒度

`simulation_OTN.py:79–91`创建ServiceManager与FailureManager，将`service_mgr.graph_updater`传给failure_mgr，再生成/调度故障。GraphUpdater的注册表按节点、链路映射任务ID并存储资源信息（Graph_update.py:46、280–303）。

| 环节 | 当前源码逻辑 | 范围解释 |
|---|---|---|
| 故障生成 | failure.py:24–63：按配置数量拆分节点/链路故障，分别采样间隔和持续时间，随机选择资源 | 没有SRLG或区域共因映射；不能当作相关风险模型 |
| 故障生效 | 65–84：failed置True；节点compute/storage或链路可用带宽置0，保存原值 | 资源状态变更，不是光路保护切换 |
| 识别任务 | 86–97：查询资源注册表 | 依赖调用方注册完整且资源键一致 |
| 任务受损 | 99–122：allocated=False，加入blocked，按任务类型调用资源释放 | 没有训练进度、剩余工作量、检查点或副本状态模型；阻塞不等于可恢复暂停 |
| 物理修复 | 124–145、185–192：等待duration后恢复保存资源值，再尝试触发等待队列 | 修复资源不等于恢复受损训练任务 |
| 原训练进程 | service.py:243–271：等待整体JCT；timeout后若allocated=False则退出 | 未调用SimPy interrupt；不是故障时刻精确停止每轮通信/计算 |
| 等待任务重试 | service.py:591–638：等待队列取任务，重新启动服务进程 | failure.py没有把受损任务加入该队列；不能解释成受损训练自动续训 |

## 这份快照的接口断点（不作论文有效性结论）

1. FailureManager持有的是GraphUpdater，却调用`release_distributed_training_resources`等释放接口（failure.py:117–122）。已读Graph_update.py仅有`release_graph_resources`等接口，未定义上述方法，未见适配层。这些分支若触发，存在AttributeError风险。
2. 物理修复后调用同一对象的`_trigger_waiting_tasks`（failure.py:133、145），但该方法属于ServiceManager，不在已读GraphUpdater中。
3. `failure_process`用一个外层try捕获整个过程（147–195）。如果任务释放处抛异常，会进入日志分支，跳过后续等待和资源修复。这是静态控制流判断，本轮未执行验证。
4. 附带`data/failures.yaml`设置`num_failures: 0`，按默认此配置不会触发上述故障路径；不说明作者从未启用过其他配置。
5. 节点故障置零compute_available，但GPU分配/释放另用available_gpu；恢复是保存值回写。多次重叠故障、故障期间其他资源变化及计数一致性需要另核验，不能把赋零恢复看作完整资源生命周期实现。

这些断点提示当前快照可能未完整整合，不代表用户自维护版本或最终论文实现必有同样问题。不在本轮擅自修复接口。

## 与第一点论文的关系

论文评估器使用配置好的故障后重路由骨干与成对波长分配；已读 `CLTC_paper_simulation.py → paper_experiments.py → paper_evaluator.py` 路径不通过FailureManager来动态触发重路由。failure.py中也未调用CLFR/波长补偿/DP容量调整。

因此两条链应区分：

- 通用事件层：资源故障→识别受损任务→标记阻塞→物理修复。
- 论文性能层：给定故障后路由→比较光/计算补偿后的迭代与等待指标。

不能把前者的阻塞/修复当成后者已实现全过程恢复，也不能因failure.py没有重路由就否定论文固定重路由之后的研究范围。第一点原文证据仍以 `research/first-point-evidence.md` 为准。
