# X02 步骤3：服务保障目标草案 v0.1

日期：2026-10-26。承接 [场景草案](scenario-draft.md)，只界定比较准则，不选择算法、不改变 HYP/GAP 状态，也不表示用户已经确认阈值或研究方向。

## 1. 保障什么

**工作目标：在光网络故障后，让当前正在生成的请求从正确状态继续，在允许的停顿内向用户交付下一个有效 token，并在恢复后维持约定的生成服务水平。**

这里“有效 token”指属于当前请求、在正确的模型和上下文状态下产生、按序交付且没有重复的输出。不能靠重发上一个 token、保活消息、占位文字或直接结束响应来满足时限。

该目标是本研究的候选保障约定，不是从某篇论文得到的统一生产 SLA。具体时限保留为参数；没有证据时不填毫秒数。单故障场景下的纸面可行性不等于对所有故障和业务负载作确定性保证。

## 2. 必须满足什么，另外比较什么

| 层次 | 草案要求 | 用途 |
|---|---|---|
| 正确性前提 | 同一请求、兼容模型与上下文，明确已确认 token 边界、在途状态及去重规则；恢复后可继续生成 | 不满足则不算成功恢复；本文不证明任意配置下数值逐位一致 |
| 故障期间保障 | 用户观察到的故障跨越 token 间隔不超过允许值 G_max | 防止“光路恢复了，但用户还长时间等不到输出”被记作达标 |
| 恢复后保障 | 在共同定义的观察窗口内检查后续 token 间隔、请求完成/终止情况 | 防止只赶出一个 token，随后持续严重变慢 |
| 网络与资源可行性 | 所有服务/状态路径及光资源配置可实现；计算、显存和其他受保业务约束成立 | 不能通过占用不存在的容量或挤掉其他业务制造成功 |
| 比较指标 | 实际停顿、恢复后延迟分布、请求达标率、终止/重试、波长链路占用随时间的积分、计算和存储成本 | 在同等保障和资源预算下比较，暂不任意加权为一个分数 |

“恢复后保障”先保留参数化约定：窗口 W 内完成请求，或若仍在生成则持续观察；对窗口内后续 token 间隔检查阈值 L 与允许超限比例 ε。也单独报告最长间隔，避免平均值掩盖长停顿。W、L、ε需根据选定任务说明或做范围分析，不代表已知生产要求。

只有一个 token 的短尾请求不能硬要求更多输出。正常EOS应记为正确完成；故障导致的强制终止不能伪装成正常完成。窗口不足时标记观察不足，不记成自动达标。

## 3. 统一计时，不能把检测时间漏掉

令 t_last 为用户最后收到一个有效 token 的时刻，t_f 为光故障发生时刻，t_d 为控制器检测并可开始决策的时刻，t_next 为用户收到下一个有效 token 的时刻。当前检查对象是 t_last ≤ t_f ≤ t_d ≤ t_next 的故障跨越间隔；若故障期间仍有有效输出，应按实际输出更新时间线。

- 用户实际看到的间隔：G = t_next − t_last。
- 从故障发生到可再次输出的耗时：T_f = t_next − t_f。
- 若要求 G ≤ G_max，则故障发生时剩余预算 H_f = G_max − (t_f − t_last)。
- 到检测时仍可用于后续恢复的预算 H_d = G_max − (t_d − t_last)；检测之前的等待已消耗预算。

因此，若方案a从检测后到有效输出的预测耗时为 R_a，达标条件是 R_a ≤ H_d，且正确性、资源与恢复后服务约束均满足。若H_d<0，本次间隔已经违约；仍应比较何时恢复和后续影响，不能通过重新起表消除违约。

R_a要包括尚未完成的决策、设备/路径配置、排队、状态准备/搬运/重建、接替切换、必要重试/重连，以及产生和交付下一个token的时间。可重叠动作按实际依赖关系取关键路径；只有明确采用串行简化模型时才能直接求和。等待原路径自行恢复也属于可比较动作，计入相同时间轴。

## 4. 光连接恢复与任务恢复分别记账

记录 t_net（恢复方案所需的连接具备传输条件）与 t_state（接替或原站点的请求状态具备继续执行条件）。下一token可能还需要排队、执行其他模型段、采样和用户交付。

所以t_net不能直接替代t_next。迁移方案甚至需要先建立状态传输连接，再建立/启用服务连接；各阶段按实际顺序记录，不能为凑一个“网络恢复时刻”忽略阶段差异。

后续光容量的需求应由状态传输、逐token交互及其依赖具体导出。不能把 G_max 直接当作所有迁移数据的传输窗口，也不能将平均TPOT直接解释成某次最长可容忍故障停顿。

## 5. 对第4步的统一比较规则

1. 对透明光路恢复、波长转换/分段转发、已有备份启用、A可达时搬运、U记录重建及等待恢复，使用同一故障时刻、资源快照和时间原点。
2. 已有备份所需的故障前存储、计算预留和同步通信必须计入；若额外给某方案预备资源，应明确作为不同预算档次比较。
3. 不能把生成长度、未来故障或实际恢复结束时间当作在线已知量。纸面分析可给条件区间，后续算法只能使用当时可观测信息或声明的预测。
4. 当前请求是最小分析单元。后续扩展到多请求时，按故障时已在运行的固定请求集合统计；失败/终止请求留在分母中，不能只统计被成功接管的请求。
5. 两个方案都达标时，比较停顿和资源代价；一个达标时才谈保障差异；都不达标时如实记违约，不能宣称满足保障。允许按两类成本展示权衡，不先设有利于迁移的权重。
